// a pad and a launch key each carry their own "Relative to" setting (see C_LaunchFrame*).

#Const C_TrampolineVariantBaseRelative 20000	// dir 0..7 = 45 deg step from the owner's aim

// pad is placed geometry, so the direction it launches in is authored in world space, while a key

// Launch abilities: the same launch, triggered by the player on keys 1-4 instead of by a pad.
// A checkpoint (or the start spawn) grants and configures them for its section; the mode binds
// one action slot per granted key and arms it with a trampoline variant when the key is pressed.
#Const C_LaunchKeyCount 4					// keys 1..4 = EActionInput::Activable1..4 = action Slot_E..Slot_H
// One action model per key, each running the same script as Trampoline.Action.Gbx. This is what
// makes several keys work at once: a bound action's press echo carries no slot and no key (every
// identity the event does carry is Slot_A), but it does carry the *model* name in Event.ActionId,
// so giving each key its own model turns the echo into an exact key id. The names below are what
// LaunchKeyFromActionId matches, path and extension included.
//
// Rebuild them by saving the action out under each name — NOT with `cp`. A Gbx carries its own
// ident near the head of the file (the four shipped here differ from Trampoline.Action.Gbx, and
// from each other, in exactly that string and nothing else), and four files sharing one ident is
// a risk none of this needs to take: the game is free to key its loaded actions by ident rather
// than by path, and if it does, ActionList_Add hands back the same model for all four, every
// press echoes the same name, and LaunchKeyFromActionId collapses the keys onto one. Distinct
// idents cost nothing and make the question moot. Index 0 = key 1.

	"TrampolineKey1.Action.Gbx",
	"TrampolineKey2.Action.Gbx",
	"TrampolineKey3.Action.Gbx",

// Charges: the weapon economy (Gain / Amount / Refill / Empty), rebuilt mode-side for the keys.
// There is no engine ammo behind an action, so the mode counts the charges itself and the
// LaunchKeys HUD layer draws them as the bar strip the native weapon gauge shows for ammo.
// Amount 0 means unlimited (the cooldown is then the only limit, which is how the keys behaved
// before charges existed) — unlike a weapon, where an amount of 0 leaves the player with no shots.
#Const C_LaunchDefaultAmount 4				// charges granted per key; 0 = unlimited
#Const C_LaunchAmountMax 10					// clamp ceiling for Meta_Launch*_Amount (and the HUD's bar cap)
// Gain is a percentage of one charge per second, so the dialog can show the weapon block's own

// travels in the Integer[] the editor's LaunchMetaRead/LaunchMetaWrite already trade.
#Const C_LaunchDefaultGain 100				// 100 % = one charge per second; 0 = spent charges never come back
#Const C_LaunchGainMax 1000					// clamp ceiling for Meta_Launch*_Gain (percent)
#Const C_LaunchChargeBaseMs 1000			// ms per charge at 100 % gain
// The native gauge pauses between charges: a charge finishes, the strip holds for a moment, then
// the next one starts filling. Firing is not what triggers it — a shot starts the next charge
// straight away — so a strip coming back from empty reads fill / pause / fill / pause. Kept as a
// percentage of one charge's fill time so it scales with Gain.
#Const C_LaunchChargeDelayPercent 50		// pause after a charge completes, % of the fill time
#Const C_LaunchDefaultRefill False			// True: entering the section tops this key back up

// How an anchor persists all four keys: ONE metadata array, Meta_LaunchConfig, rather than a
// Meta_Launch<Key>_<Field> name per field. Metadata names cannot be composed at runtime, so the
// scalar form had to spell out 4 keys x 12 fields three times over (editor read, editor write,
// mode read) and still could not be written in one function under the linter's statement cap.
// Array metadata for an anchor was verified to survive a map save/load in this engine version
// (2026-08-17): stored per anchor, length preserved, readable from both the editor and the mode.
//
// Layout: C_LaunchKeyCount blocks of C_LaunchFieldCount, key 1 first — so key K field F sits at
// (K-1)*C_LaunchFieldCount + F. A key whose whole block the array does not reach is read as
// unconfigured (the editor shows the defaults above, the mode grants nothing), so an absent or
// truncated array grants no keys at all. Appending a field moves every later block, which leaves
// anchors saved before it short: they read as unconfigured until the editor rewrites them.

// How a key press reaches the mode: the action reports its own activation (SendRulesEvent
// "press" -> OnActionCustomEvent), the way Nadeo's key-bound shield action and
// Actions/Sneak.Script.txt do, and the mode reads the key off Event.ActionId. The two
// alternatives were tried in-game and are dead ends, recorded here so they aren't rebuilt:
//   - the engine's OnActionEvent does carry the key (EActionInput::Activable1..4) but is
//     delivered ONLY for inputs with no action bound, so it never reports a usable ability;
//   - polling each slot's cooldown stamp never moves: a Cooldown the action script sets is
//     reported by Action_GetState but never actually starts (CooldownStartTime stays -1, and
//     Action_GetRemainingCooldown stays 0).
// Which action slot actually fires a key launch. A key launch is the very same launch a pad
// fires, so routing it through the pad slot (Slot_D) costs nothing and keeps one firing
// instance per player: the key slots (Slot_E..H) then only carry the bind — HUD icon and
// press echo. Introduced while a bound slot was suspected of dropping variant writes; that
// turned out not to be the bug (an unmasked Variant read was), so either setting works.
//   True  = arm Slot_D on a key press (pads and keys share one firing instance).
//   False = arm the key's own slot.
#Const C_LaunchFireOnPadSlot True
// One launch at a time per firing instance. The action's fire latch (State_Boolean1 in
// Actions/Trampoline.Script.txt) is cleared ONLY by a tick on which it reads its Variant back as
// 0, and it reads that Variant once per tick — so the mode must never write a disarm and the next
// arm into the same instance without leaving a loop pass in between. It would only ever see the
// second value, the latch would stay set, and a latched instance never fires, so it never echoes,
// so the mode never disarms it again: the slot is wedged for the rest of the map. That is exactly
// what rapid fire used to do (a fire echo and the next press land in one pass), and the symptom
// is the giveaway — the charges keep discharging, because every gate the mode owns still passes,
// while nothing launches. One pass is provably enough (mode and action each run once per tick, so
// exactly one action read falls between two consecutive passes); the second buys a tick of slack.
#Const C_LaunchSlotRearmPasses 2
// Safety net for an arm whose fire echo never comes back — the action only fires while its owner
// is spawned, so a launch armed on the tick a player dies is simply never acknowledged. Without
// it the slot would count as busy forever. Generous next to the ~2 ticks a real echo takes.
#Const C_LaunchSlotArmTimeoutMs 500
